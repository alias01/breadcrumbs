# Step 3 — Implement

0. **Before task 1.**
   - **Branch:** `git branch --show-current`. Not `feature/<this story's slug>` → `git checkout -b feature/<slug>` from the default branch (from the current branch only if this story depends on that unmerged one — say so; Step 4 Dependencies then names the base). One line: `On feature/<slug> (from main)`. Never commit a story onto another story's branch.
   - **Checkpoint:** full mode, ≥4 tasks → read `context-file-mechanics.md` + `context-template.md`, create the file, backfill Original Story / Understanding / Assumptions / Plan / Flow / Task Checklist, trip marker, stop with: `Plan saved to .breadcrumbs/context/<slug>.md — run /compact now; I'll resume from the file.` Next user message isn't a compaction → one line `Not compacted — continuing at ~<N>k context`, then proceed; don't ask again. After compact/resume the file is the whole state; don't re-read the transcript. <4 tasks or lite → skip.
1. One task at a time. **No text-only turns.** Between the first edit and the gate, every assistant message contains a tool_use block. The only text allowed is one line, shape `✓ Task N — <verdict, ≤8 words>`, written *in the same message* as the next task's first tool call — a `✓` line sent on its own is the violation, not the fix. No "starting N", no "now task N+1", no "server started", no "good —". A message with text and no tool call is a point-7 break, nothing else. Nothing committed (6). Re-read this point before the first edit, not at the gate.
2. **Don't ask mid-task.** Judgment call → Task Log "Why". Contradicts the plan or needs a scope decision → Scope Changes, flag immediately.
3. `ponytail`: simplest thing that works, existing deps first, no unrequested abstractions. Never simplify away validation, error handling, security, accessibility, or the scale target — "works" means at that scale.
4. **Test first, verify before checkoff.** Done = something demonstrates it works. **Every verdict below goes to the Task Log or held note, never chat.**
   - **Red, before any implementation edit — every task, every type, lite included.** Write the task's smoke test (2.4), run it, confirm it fails *for the expected reason*: missing route/function/element, wrong value — not a syntax, import or setup error. → `Red: <test file> › <name> — <failure, one line>` (repo-relative path first: the freeze hook reads it). Bug fix → regression test red on the unfixed code. Refactor → characterization test *green* on current code, own task first, read-only for the story (`Red: n/a — characterization, pins current behavior`). Nothing executable (types-only contract task, docs) → `Red: n/a — <why>`.
   - **Frozen after red.** That test's assertions don't change for the rest of the story — needing to is a 7 Scope Change, never a silent edit. Setup/fixture plumbing may change; assertions and the contract fixture (`step2-plan.md` 6) may not. Opt-in enforcement: `hooks/freeze-tests.mjs`.
   - **Green:** implement until it passes. Judge by exit code + stderr, never a printed summary.
   - Run the 2.4 cases mapped to this task (lite → the named check). None mapped → repo fast checks over what you touched, name which. **Per task: the touched spec only.** Full suite once, at 8.
   - Nothing executable → say so + what was inspected. Silence isn't a verdict.
   - Fails → fix, re-run. Cause is the plan → 7.
   - **Self-review:** diff vs the task's Why — scaffolding, TODO-as-fix, workaround where root cause was the point, unasked abstraction. A smoke test that would still pass with the feature deleted doesn't count — minimal means fewer tests, not weaker ones. Fix now.
   - **Scale scan:** query/call per item of a growing collection, unbounded load, new query without pagination/index, sync work on a hot path. Trivial → fix, note in `Verified:`. Not trivial or target can't hold → not a checkoff, 7.
   - **Full-suite rule:** per task the touched spec only; gate 8 runs *both* the backend suite and the frontend suite, named, even when only one side changed.
   - **UI change → look at it.** Check the tool list (Claude Browser, `run` skill, simulator) before claiming none; SSR grep is the fallback, said as such.
   - **Dev servers:** `lsof -i :<port>` before the first start; taken → **never kill it** (it's the user's), start on a free port with the client env in the same command. Log filtered to `grep -Ei "started|local:|ready|EADDRINUSE|error"` (Nuxt/Vite print `Local:`, not "started").
   - **Manual E2E → one script per story**, in the repo's own package dir (so imports resolve), env loaded the way the repo's own config does (`import 'dotenv/config'` if `prisma.config.ts` does), each scenario a function, run once, prints only asserted fields, cleans up, deleted after. Adding a scenario = editing that file, not writing a second one. Never one `curl` per turn.
   - **CLI usage error** → `<cmd> --help | grep <flag>` once, then the fixed call. No second guess, no full help text.
   - Outcome → `Verified:` (what ran, what it showed). Step 4's Test section comes only from this.
5. **Manual-edit review** — before each task and on resume: `git status` / `git diff HEAD` over the story's files. A change you didn't make → one-line `Check:` (correct, or issue: what/where). File off the Flow (2.6) → say so, non-blocking. Review, not veto: the edit stands unless it breaks something.

   After each task: file exists → append Task Log entry with `Red:` + `Verified:`, tick the box, one write, trip marker. Forms (`context-template.md`): judgment call → What/Why block; mechanical → one line; hand-edit → line + `Check:` (+ `Flow:` if off-plan). No file → hold the same as a private note for 8. Nothing sent to the user now.

   **Learning from the edit:** hand-edit or spoken correction that reads repo-wide (always strips X, always adds guard Y, "we never do X here") → ask once: "Save that as a standing project rule?" Yes → append to `.breadcrumbs/constitution.md`, apply from the next task. No → don't ask again for that pattern.
6. **Don't commit per task.** No `git add`/`commit` until 8's review is approved. No curiosity checks either (`git branch`, `git log`) — only calls that gate the next action.

   After approval: one commit per task, in order, mirroring the Task Log — the whole loop in as few Bash calls as possible, no text between commits. Conventional Commits `<type>(<scope>): <imperative summary>`; body = short bullets from What/Why. Types: `feat` `fix` `docs` `style` `refactor` `perf` `test` `chore` `revert`. Reverting a landed task (Scope Change after approval) → `git revert <hash>`, header rewritten to `revert(<scope>): <what was undone>`, hash + reason in body. Scope change mid-task → still one commit; type = what shipped. Check headers with `validate-commit-message.mjs -m "<header>"` (resolution in `context-file-mechanics.md`; `-m` takes the header string, a bare argument is read as a file path); not found → by hand.
7. Test fails / assumption invalidated / scope changes / **scale regression** → Mid-flight break (`SKILL.md`). Then: Scope Changes entry (date, trigger, before/after, affected tasks, why), amend Current Requirements in place, update Assumptions/Plan/Checklist. Scale case: tell the user immediately — what regressed, against which target, what it takes to hold — before fixing. Absorb or fix is the user's call.
8. **Gate:** all tasks ticked → **run the whole planned test set** (every 2.4 case + backend suite + frontend suite, each named with its count) against the uncommitted tree. Any text-only turn since the first edit → one line at the top of the review admits it.
   - Red → fix, re-run; cause is the plan → 7. Never present with a known-failing case.
   - Nothing runnable → say so with what was checked, continue.
   - Green → **one review message, nothing committed:** per task — name, files (`git diff --stat`), and **what to check** (the risky assumption or exact behavior, or "mechanical, low risk").
     - Approved → commit every task in order (6), then summarize what was built and what proved it (cases + outcome, scale target measured or scanned). Stop for PR confirmation (`step4-pr.md`).
     - Issue flagged → fix in place (uncommitted), re-present only the affected task(s).

   **Review round, not a fix-per-message loop.** A question → answer inline, no edit. A requested change → note it; if another question or change lands before you've applied it, hold both and apply together — a single, unambiguous "fix this now" is done immediately, no hold. Re-run only the spec(s) touched by the held batch, never the full suite; full suite reruns once more, right before approval, not per fix. Re-presenting a fix restates only what changed, not the whole point-8 message again.

   **Review running long** (3+ fix rounds, or the user says "pause"/"continue later") → same checkpoint as 3.0: file exists → suggest `/compact`; no file yet → create one first, backfilled to the review state.

   Step 4 drafts from these commits; a fix after commits land is its own commit and Log entry (6's revert path).
